## Architecture

Hotpoint Apps Hub is an internal Next.js 16 (App Router) portal for submitting/approving requisitions — IT equipment, travel, salary advances, and physical access/keys — plus two SSO-embedded internal systems (IT HelpDesk, Staff Product Purchase).

### Auth & session model

- Sign-in is a manual Microsoft Entra ID OAuth/PKCE flow using `arctic` (`app/api/auth/login`, `app/api/auth/callback`). Failures redirect to `/login?error=sso_unreachable|auth_failed|invalid_state`, which the login page shows as a notice. `lib/microsoftSso.ts` hardens the Entra ID callback: the authorization-code exchange is retried once **only** when the connection never opened (`retryOnConnectFailure` - codes are single-use, so a reset mid-request isn't retried), `/oidc/userinfo` goes through `fetchMicrosoftProfile` (timeout, one retry, throws on non-2xx instead of treating Graph's error body as a profile), and a profile without an email is rejected.
- The callback also upserts the user into `users` (`recordSignIn`, `lib/users.ts`: name refreshed, `last_sign_in_at` set; a failure is logged, never blocks sign-in), so Settings can list everyone who has signed in.
- After the Entra callback, the app issues its **own** session: a `jose`-signed JWT in an httpOnly cookie `requisitions_session` (`lib/session.ts`, 7-day expiry). All server-side auth checks read this cookie, not the Entra token.
- Accounts can be **deactivated** (`users.deactivated_at`, migration `031_user_deactivation.sql`, Settings' Users & roles tab: `deactivateUser`/`reactivateUser` in `serverActions/UserRoleAdmin.ts`). The callback refuses a deactivated user before issuing a session (`/login?error=account_deactivated`), and `getSession` checks `isUserDeactivated` (`lib/users.ts`) on every request, so an existing 7-day cookie stops working on the next request. Don't add a session read that bypasses `getSession`. The check fails open on a database error, since a failure there would otherwise sign everyone out. A user without a row is active. Deactivation keeps roles (reactivating restores them) and is refused for yourself, for the last active `config-admin` (`removeRole` uses the same active-holder count), and for anyone still in an approver `_array`, since approval links work without a session. Remove them on the Approvers tab first, and `addApprover` refuses deactivated users.
- Emails are stored and compared **lowercase** everywhere: `lib/session.ts` lowercases the session email (also when decoding older cookies), and migration `020_lowercase_emails.sql` lowercased existing data and added `CHECK (x_email = LOWER(TRIM(x_email)))` constraints on `users` and every `_array` table. Rows added to those tables by hand must be lowercase. Plain `=` email matching in SQL relies on this.
- Submission routes take the submitter's name/email from the session, never from the request body.
- Route gating is `proxy.ts` at the repo root, **not** `middleware.ts` — Next.js 16 renamed the convention. It redirects unauthenticated `/dashboard/*` to `/login?returnTo=…` (sign-in lands back on that URL, so public pages can link straight to dashboard forms), and bounces already-authenticated users away from `/` and `/login` to `/dashboard`, and from `/advance` to `/dashboard/advance`.
- `app/(protected)/dashboard/layout.tsx` is the second gate: re-checks the session, loads roles via `serverActions/GetUserRoles.ts` (Postgres join `users` → `user_roles` → `roles`, defaults to `["user"]`), and wraps children in `UserProvider` (`context/UserContext.tsx`).
- The same layout also computes `ApproverMemberships` via `serverActions/GetApproverMemberships.ts` (`lib/approverMemberships.ts`) — per-array approver flags (HOD — any `hod_array` row, assigned-HOD candidate or alternate; Security, IT, Director, Retail Director, plus per-form HR permissions) found by checking the session email against each stage's `_array` table — and passes it into `UserProvider` alongside roles.
- `(approvers)` route group (`accessapproval/[uuid]`, `itapproval/[uuid]`, `travelapproval/[uuid]`) is reached via emailed links and is token-gated per-UUID, independent of the logged-in session — don't assume `getSession()` applies there. Their page chrome is `components/Approvers/ApproverShell.tsx`, chosen by the session alone: a signed-in visitor gets the normal dashboard shell (`components/Dashboard/AuthenticatedShell.tsx`, shared with the dashboard layout) under their **session** identity, so its nav links to the requisition form pages, which submit as who they say; a visitor without a session gets the public `PageShell` with no requisition links (every submission route needs a session) and a Login that returns to the approval URL. Every outcome renders inside it, status screens included (`InvalidToken`, `AlreadyProcessed`, `NotFoundRequest`, `NotAssignedHod`, `PushbackUnavailable`): each page's default export wraps an `ApprovalPageContent` component in `ApproverShell`, so new early returns get the shell for free. Each route's `loading.tsx` also renders its skeleton inside `ApproverShell`, so the skeleton shows in the right shell while the page loads the requisition on the server (it's the app's only use of `loading.tsx`). Those screens hide their "Go to Homepage" link from signed-in viewers (`useIsSignedIn` in `context/UserContext.tsx`), who already have the dashboard nav. Never build a `UserProvider` from the approval token — the shell would show one identity while the forms submit as another. The approval modals send only the link's `token` and the `Update*Status` actions resolve the acting approver from it (`resolveApproverByToken`, `lib/approverToken.ts`, which also applies the HR `hr_forms` scope) — never trust a client-supplied approver name/email, since server actions are directly callable. On the HOD stage the pages also run `getHodPageAccess` (`lib/hodAssignment.ts`) before loading any details, showing `NotAssignedHod` to anyone who isn't the assigned HOD or an alternate (or is the submitter).

### Route groups (`app/`)

- `(protected)/dashboard` — authenticated area. Nested groups: `(embeddings)` (HelpDesk / Staff Purchase SSO iframes), `(pdfs)` (PDF viewers, e.g. `casualpdf`), plus `advance` (salary advance) and `employeeview` (session-gated, read-only Employee Requisition viewer — no PDF export, so it deliberately lives outside `(pdfs)`).
- `(approvers)` — public, per-UUID approval pages for approvers acting on emailed links (`casualapproval`, `employeeapproval`, etc.).
- `advance/page.tsx` and `login/page.tsx` are public entry points gated by `proxy.ts`.
- 404s: `app/not-found.tsx` (public `PageShell`) handles unmatched URLs and `notFound()` outside the dashboard. `(protected)/dashboard/not-found.tsx` renders `notFound()` under `/dashboard` inside the signed-in shell, and the `dashboard/[...missing]` catch-all sends unmatched dashboard URLs there. Both share `components/NotFoundCard.tsx`. `not-found` files can't export metadata, but a page that calls `notFound()` still contributes its own, so such pages return `NOT_FOUND_METADATA` (`lib/notFoundMetadata.ts`) for the tab title — the amend pages do so from `generateMetadata` for a malformed id.
- `api/` — form submission routes (`{access,it,travel,casual,employee}requisition/submitrequisition`, plus `{travel,casual,employee}requisition/submitamendment`), auth routes, the dashboard's read endpoints (`api/dashboard/tables/[type]`, `api/dashboard/summary` — see "Dashboard tables & navigation"), mail triggers, `CRON_SECRET`-gated scheduled triggers (`api/triggers/*`), `REVALIDATE_TAG_KEY`-gated cache revalidation (`api/revalidate-tag`), the Excel report downloads (`api/reports/[type]` — see "Reports"), the analytics figures (`api/analytics/[type]`, plus `api/analytics/casual/budget` — see "Analytics"), and `api/employeerequisition/attachment/[attachmentId]` — an authenticated file-streaming route (session or approver-token gated) since Employee Requisition attachments are stored on disk under `UPLOAD_DIRECTORY`, outside `public/`. Its `/preview` sub-route renders `.doc`/`.docx` and `.xls`/`.xlsx` attachments as inline HTML (via `mammoth` and `exceljs` respectively) instead of forcing a download; other file types fall back to a "use Download" page. Both serve only live attachments unless the URL carries `archived=1`, which looks the id up among files an amendment replaced or removed instead, under the same access rules (`lib/attachmentAuth.ts`) — so a link to a replaced file in an old email 404s rather than showing an outdated document.

### Dashboard tables & navigation

The dashboard home (`/dashboard`, `components/Dashboard/UserDashboard.tsx`) renders no tables. It shows counts — "Needs your approval" cards per requisition type (with a per-stage breakdown for multi-stage approvers) and "Your requisitions" cards — plus quick actions (`DashboardQuickActions.tsx`), all from a single `GET /api/dashboard/summary` request (`hooks/useDashboardSummary.ts`, query key `DASHBOARD_SUMMARY_KEY`, refetched on every mount; forms that change counts invalidate it). The tables live on one page per type — `/dashboard/{travel,it,access,casual,employee}`, each a thin `page.tsx` rendering `components/Dashboard/RequisitionTypeDashboard.tsx` — split into **My Requisitions / Pending Approval / History** tabs (`?tab=mine|pending|history`; an unavailable tab falls back to `mine`). Only the active tab's tables mount, so only they fetch. The Pending tab carries a count badge from the summary, and a pill row switches type while keeping the tab. The sidebar is unchanged: the home cards and that pill row are the navigation.

`lib/dashboardTables.tsx` is the single source of what a viewer sees: `DASHBOARD_TABLES` lists every table (key `${type}-${dataFlag}`, tab, stage label, `isVisible(roles, memberships)`), used by the type pages to pick tabs and tables and by the summary route to pick what to count (mine + pending only, never history). Keep each `isVisible` in step with the server-side gate in that type's loader. IT admins' History tab holds `itAll` instead of the HOD history. `tableEmptyCopy` gives each tab its empty state ("You're all caught up" for pending queues). `RequisitionTable` always renders (an empty table shows its empty state compactly, with no headers, search or pagination; a failed fetch shows Try again), and a collapsed table (`useTableCollapseStore`) doesn't fetch until expanded.

Table data is read through `GET /api/dashboard/tables/[type]?flag=…&page=…&pageSize=…&search=…` (`fetchDashboardTable` in `lib/dashboardApi.ts`), **not** server actions: Next.js dispatches server actions one at a time per client, so tables loading together queued behind each other. The `serverActions/Get{Type}RequisitionData.ts` loaders are therefore `server-only` modules, not `"use server"` actions — don't turn a dashboard read back into a server action. `lib/dashboardLoaders.ts` maps type → loader and rejects unknown flags; each loader still does its own session and role/membership check. Each requisition type has its own `{Type}RequisitionsDashboard/` folder under `components/Dashboard/` (table + details modal) — `TravelRequisitionsTable.tsx`/`TravelDetailsModal.tsx` sit directly under `components/Dashboard/`, while IT, Access, Casual, and Employee each have their own subfolder.

Each requisition type also has one read-only **approval history** table (`dataFlag: "history"`, keys `{type}-history`) for approvers, scoped server-side in `serverActions/Get{Type}RequisitionData.ts` to the union of every stage the user is involved in: rows where they are the assigned HOD (whoever acted) or acted on the HOD stage as an alternate, plus — per stage membership/role — every request that reached (or was auto-approved past) that stage. Conditional stages only see their own requests (Travel Director: Tier 3 only; Retail Director: retail only), and requests declined before a stage are hidden from it. IT history is HOD-only because IT admins already get the full history (with export) from `itAll`. History modals map `history` to the `"user"` stage, so they never offer an approval action. Every non-`userData` flag is checked on the server (`_array` membership via `getApproverMemberships`), never trusted from the dashboard's UI gate. That includes IT's `itPending`/`itAll` and `requisitions-export` (`it_array`) and Travel's `hrPending`/`directorPending` (`hr_array` with `travel` in `hr_forms` / `director_array`). Approver access never comes from roles: the old `hod`, `it`, `director` and `hr-travel` roles were dropped (migration `028_drop_approver_roles.sql`), so an approver's dashboard queue always matches who gets the emails and whose token works. Roles are only for non-approver access (`hr-advance`, `config-admin`, `reports-*`).

### Dashboard frame

On desktop the page area (`#dashboard-wrapper` in `components/Dashboard/DashboardWrapper.tsx`) is a square scroller inset in a red frame; four corner overlays paint the frame color over its corners so it reads as rounded. The sidebar width, the gap around the page area and its corner radius are `@theme` tokens in `css/globals.css` (`--spacing-dashboard-sidebar`, `--spacing-dashboard-gap`, `--radius-dashboard`, used as e.g. `custom:left-dashboard-sidebar`, `custom:rounded-dashboard`) — use them rather than literal `left-20`/`*-2`/16px values so the sidebar, page area and overlays stay aligned. Corner radii elsewhere use the three radius tokens, also in `@theme`: `rounded-surface` (cards, panels, modals), `rounded-control` (buttons, inputs, tabs, icon tiles) and `rounded-compact` (anything under ~30px tall, where the control radius would read as a pill) — not literal `rounded-lg`/`xl`/`2xl`/`3xl`. `rounded-full` is only for status badges/chips, initials avatars, spinners and progress bars. The react-pdf `tw()` files (`*RequisitionPdf.tsx`) have their own Tailwind config without these tokens and keep literal radii. Inside a rounded `overflow-hidden` panel, don't give the scroll container its own background — put it on the panel. Chrome can paint an opaque scroller's background on a layer that ignores the parent's rounded clip (a modal's bottom corners went square for the Key & Access form, whose terms box is a nested scroller). The desktop rail (`components/DashboardSidebar.tsx`), the mobile drawer (`components/MobileHeader.tsx`) and the logo's app launcher (`components/DashboardBrand.tsx`, which adds Microsoft 365 links with icons from `public/icons/m365/`, search keywords and a per-browser "Recent" row) all render from `lib/dashboardNav.ts` (groups, labels, icons, search `keywords`, `isNavItemActive` — a requisition is active across its whole `/dashboard/{type}` area); add nav pages there, not in either component. The rail measures its height and moves the items that don't fit into a More menu (`components/SidebarMoreMenu.tsx`) placed after the last one; the drawer is a native `<dialog>` (`.modal-drawer`) showing every item in sections. Pages scroll inside `.layout-scrollbar` containers, not the window, so multi-step forms move between steps with `scrollPageToTop` (`utils/scrollPageToTop.ts`).

### Modals

Every modal uses `components/Modal.tsx`, built on the native `<dialog>` opened with `showModal()` (styles under "Modals" in `css/globals.css`): `Modal` for content (full screen on phones with its `actions` in a bottom bar, a centred card from `sm` up; optional `footer`, and `overflowVisible` for short forms whose popovers must extend past the card) and `AlertDialog` for confirmations (a bottom sheet on phones). Escape, focus containment and the inert page come from the browser, and enter/exit are CSS transitions, so a modal stays mounted while closed: keep rendering its last content after `open` turns false (tables keep the selected row; `useLastDefined` covers parents that clear their data on close). A modal dialog sits in the top layer and makes the rest of the page inert, so anything portaled to `<body>` renders beneath it — which is why the toast (`components/Modules/Alert.tsx`) is a manual popover, and why a modal opened from inside another must itself be a `Modal`, not a `ClientPortal` overlay. Content that loads after a modal or page opens gets a pulse skeleton shaped like it (`components/Skeletons/`); spinners are only for buttons and full-screen transitions. Route changes get the top progress line (`components/LoadingLine.tsx`, mounted in the root layout) automatically: `onRouterTransitionStart` in `instrumentation-client.ts` starts it for every push/replace to a different path (not `?tab=`-only changes or back/forward), it appears only if the navigation is still pending after 150ms, and it fills and fades when the path changes (or gives up after 15s) — so links and `router.push` need no manual trigger.

### Requisition form pages

Every requisition form is its own page under its type's dashboard page: `/dashboard/{travel,it,access,casual,employee}/new`, plus `/dashboard/{travel,casual,employee}/[requestId]/amend` for the submitter's amendments. Build these URLs with `newRequisitionHref`/`amendRequisitionHref`/`myRequisitionsHref` (`lib/dashboardTables.tsx`) rather than by hand. Every launcher (sidebar, mobile drawer, `DashboardBrand` app menu, quick actions, type-page header and table empty states, details-modal Amend buttons) is a plain link. Each `page.tsx` is a thin server component that wraps the form in `components/Dashboard/RequisitionFormPage.tsx` (a back link to the type's "My Requisitions" tab). The amend pages pass `key={requestId}` so moving between two amendments remounts the form, and they do no access checks of their own: the form's `get{Type}AmendmentContext` action checks submitter and eligibility (shows "can no longer be amended" otherwise), and the amendment route checks again. Those context queries use `staleTime: 0`/`gcTime: 0` so a form is never seeded from a copy that predates a later amendment.

A form with input it would lose calls `useReportUnsavedChanges` (`components/Dashboard/UnsavedChangesGuard.tsx`, provided by `DashboardWrapper` around the navs too). While it reports changes, same-origin link clicks are caught in the capture phase (`preventDefault` only, so the link's own `onClick` still closes menus/drawers) and the "Discard this form?" dialog asks first; the sidebar Back button goes through `useConfirmLeave`; refresh/close get the browser's `beforeunload` prompt. The browser's own Back button can't be intercepted in the App Router and is deliberately unguarded. Any new programmatic navigation away from a form page (`router.push`/`back`) should go through `useConfirmLeave`. After a success the forms clear their input (so leaving no longer asks) and `AlertModal` offers "View my requisitions" (`successLink`); an amendment's success button goes there directly.

### Approval workflows

The HOD stage is not array-based: it belongs to the single **assigned** HOD auto-selected (or manually overridden) at submission and stored on the requisition row (`*_hod_email` / `hod_approver_email`), plus that HOD's permanent **alternates** (migration `018_hod_alternates.sql`). Alternates are themselves `hod_array` rows (so their `hod_uuid` is their approval token) linked through `hod_alternates(hod_id, alternate_id)`; rows flagged `hod_array.is_alternate_only` are never offered in the submission dropdown/auto-select (`loadHodArray`) and are rejected by the server-side HOD lookup (`resolveHod` in `lib/hodAssignment.ts`, used by every submission and amendment route). The forms send the selected HOD's **email** (`hod_email` is unique, names are not); `resolveHod` looks it up and the stored name comes from `hod_array`. The assigned HOD and all alternates (minus the submitter) get the "Action Required" email and see the request in their pending queue; first click wins. The update actions (`serverActions/Update*Status.ts`) enforce this with `getHodActionError` (`lib/hodAssignment.ts`): the actor must be the assigned HOD or one of their alternates — not merely in `hod_array` — and never the submitter. Acting on the HOD stage no longer overwrites the assigned HOD email; the actor's email goes in `*_hod_actioned_by_email` (the `*_hod_approver`/`hod_approver_name` name column is still overwritten with the actor's name, so displays show who acted). Only the actor gets the HOD-stage confirmation, and every later-stage email (and Travel push-back email) goes to the actor, not the assigned HOD. HOD history shows the assigned HOD everything assigned to them and an alternate only what they acted on (`hodPendingScopeSql`/`hodHistoryScopeSql`); detail/attachment access goes through `isHodViewer`. Because the name column holds the actor, Travel/Casual amendments prefill the form with the assigned HOD's email, detect a HOD change by email, and record the change by name (the previous name resolved from the stored email via `assignedHodNameSql`), and an amendment resets `*_hod_actioned_by_email`. HODs, their department/alternate-only flags and alternates are managed on the Settings page's Approvers tab (see "Settings"), which expires the `GetHodArray` tag. The dashboard's HOD tables are gated on `ApproverMemberships.isHodApprover`. Every stage after the HOD stage — IT, Security, HR, Director, Retail Director — is fully array-based: `ApproverMemberships` checks membership by exact email match against that stage's `_array` table, and any member of that array can act on a pending item (first click wins, no "assigned to me" column). Because an array token works on any requisition of its type, every approval page shows `StageNotReached` (`components/Approvers/StageNotReached.tsx`), and every `Update*Status` action refuses, for a stage whose earlier stages haven't all approved (a stage still pending after an earlier decline counts as not reached). The dashboard queues already filter on the earlier stages.

Each requisition type has its own multi-stage chain under `utils/`:

- `utils/ITApprovalStages/` — hodApprovalStage → itApprovalStage
- `utils/AccessApprovalStages/` — hodApprovalStage → securityApprovalStage
- `utils/TravelApprovalStages/` — hodApprovalStage → hrApprovalStage → directorApprovalStage. HOD and HR are mandatory for every tier (`hodApprovalStage` always forwards to HR); only the cost tier from `utils/calculateTravelApprovalTier.ts` decides whether Director is added — Tier 1 and Tier 2 finalize at HR, Tier 3 adds Director. The thresholds (today ≤30K Tier 1, ≥100K Tier 3) are effective-dated rows in `travel_tier_thresholds` (migration `027_requisition_options.sql`, scheduled on Settings' Travel tab, tag `GetTravelTiers`); the thresholds in effect on the submission or amendment date (Nairobi) apply (`loadTravelThresholdsToday`), the form sends the tier it showed as `expectedApprovalTier`, and `validateTravelFormData` rejects a mismatch with a 409. The form's tier cards and the guideline's (`TravelTierCards`) show the live thresholds. Any travel-HR member can **push back** (reverse) the recorded HR decision, approved ↔ declined (it must flip the status), from a Push-back button in the dashboard's travel history modal. The button opens the HR approval page with `&mode=pushback`; that parameter is presentation only. `serverActions/PushbackTravelHrDecision.ts` makes the change in one transaction with no intermediate `pending` state: it resolves the actor from the HR token, locks the row, re-checks the rules in `lib/travelPushback.ts`, copies the old decision into `travel_hr_pushbacks` (migration `016_travel_hr_pushbacks.sql`) and overwrites the `travel_hr_*` columns. The rules: HR status not pending, not Tier 3 (even if the Director stage was auto-approved), fewer than 3 push-backs, and on or before `travel_departure_date` in Africa/Nairobi time. `travel_hr_pushback_count` doubles as the optimistic-concurrency token. Emails go out via `utils/TravelApprovalStages/hrPushbackStage.ts`: to the actor, submitter and HOD, plus Finance — a dedicated "Reversed" email for approved → declined, or the normal final-approval email for declined → approved. Push-back history (`components/Approvers/TravelApprovers/TravelPushbackHistory.tsx`) is shown in the details modal, the approval page, the PDF view and generated PDF, and the travel email template. The original submitter (only) can also **amend** any form field until HR approves (a HOD or HR decline is still amendable) and on or before the departure date — rules in `lib/travelAmendment.ts`, which reuses the push-back departure-date window. `app/api/travelrequisition/submitamendment/route.ts` locks the row, re-checks the rules, recomputes the tier server-side, resets every approval stage (HOD/HR `pending`; Director `pending` for Tier 3, else `N/A`), reproduces the self-HOD auto-approve branch, and records the change in `travel_requisition_amendments` (reason, tier/total before and after, snapshot of the decisions it reset) plus one `travel_requisition_amendment_fields` row per changed field keyed by the `TravelFormData` key (migration `017_travel_requisition_amendments.sql`). Push-back history and `travel_hr_pushback_count` survive an amendment — the 3-push-back cap is for the requisition's life. `travel_requisitions.amendment_count` is a second optimistic-concurrency token, checked under `FOR UPDATE` by the amendment route, `UpdateTravelStatus` and `PushbackTravelHrDecision`, so no approver or push-back acts on content amended mid-review. Emails go out via `utils/TravelApprovalStages/amendmentStage.ts`. Amendment history (`TravelAmendmentHistory.tsx`) appears everywhere push-back history does; the dashboard modal loads both through `serverActions/GetTravelAuditTrail.ts`. Validation shared by the submission and amendment routes lives in `lib/travelRequisitionRules.ts`
- `utils/CasualApprovalStages/` — hodApprovalStage → hrApprovalStage (no Finance stage, no tiering); like every other flow, the HOD stage is the single HOD selected at submission (stored in `casual_hod_email`), and only HR is array-based (`hr_array` — any member can act, first click wins). On HR approval, a generated PDF summary is attached to the HR approver's confirmation email and to a notification sent to the external casual-labor provider (`EXTERNAL_CASUAL_PROVIDER`); `loadFinanceArray()` in `lib/loadApprovers.ts` is kept but unused by this flow. The original submitter (only) can amend the requisition — any header field or section — any time until HR approves it (`isCasualAmendableHrStatus` in `public/assets.ts` — a HOD or HR decline is still amendable; a HOD approval is not a barrier). Amending fully resets both `casual_hod_*` and `casual_hr_*` approval columns to `pending`/`NULL` and restarts the chain from HOD (reproducing the self-HOD auto-approve branch when the re-resolved HOD is the submitter), recording a diff row per amendment in `casual_requisition_amendments` (header fields) and `casual_requisition_amendment_sections` (per-section fields, matched by the now-stable `UNIQUE(request_id, section_name)` identity) via `utils/CasualApprovalStages/amendmentStage.ts` and `app/api/casualrequisition/submitamendment/route.ts`. `casual_requisitions.amendment_count` doubles as an optimistic-concurrency token — both the amendment route and `UpdateCasualStatus` check it under `FOR UPDATE` so an approver can't act on a version superseded mid-review. There is no mechanism to change a requisition once HR has approved it (this is an accepted gap, not an oversight) and no submitter-initiated withdrawal — a corrective amendment is the only way to undo one. This replaced the earlier "HR can adjust the final approved headcount per section" behavior (and the `hr_approved_casuals` column), since changes now have to originate from the submitter
- `utils/EmployeeApprovalStages/` — HOD → Retail Director → HR → CEO (Director). Requisitions submitted before migration `034_employee_hr_before_ceo.sql` finish on the original HOD → Retail Director → CEO → HR order; `employee_requisitions.hr_before_director` tells them apart (set `TRUE` by the submission route, and by every amendment, which moves an older requisition onto the new order). Every order-dependent check — next stage, whether a stage has been reached, the final stage, amendability — goes through `lib/employeeApprovalOrder.ts` (`employeeStageReachedSql` is its SQL twin for the dashboard queues/history and `lib/approverPendingWork.ts`); never hard-code the stage order. `UpdateEmployeeStatus` and the approval page refuse a stage the requisition hasn't reached (`StageNotReached`), since an array token works on any requisition. All decision emails come from `employeeApprovalStage` (`approvalStage.ts`), which forwards to the next pending stage or, when none is left (or on a decline), notifies everyone involved. Displays list a requisition's stages in its own order through `employeeDisplayStages` (details modal, `employeeview`, approval page, email template; amendment history uses `nullified_hr_before_director`); the dashboard table, report columns and guideline use the new order, and the report adds an Approval Order column and "Days to Final Decision". Retail Director is conditional: it only applies to requests from a department flagged `requires_retail_director` (see "Departments" below), and is skipped even then if the HOD is themself a Retail Director. The flag is read only at submission and amendment, which store `employee_retail_director_approval_status` as `pending` or `N/A`; every later check (approval page, `UpdateEmployeeStatus`, modals, email template) reads that stored status, never the department. Director and HR are mandatory for every request. A HOD who also holds a later role isn't asked twice, and the two checks are independent: a Retail Director HOD auto-approves the Retail Director stage when the HOD stage approves (by hand in `UpdateEmployeeStatus`, or automatically when the submitter is their own HOD — `applySubmissionAutoApprovals` in `utils/EmployeeApprovalStages/submissionStage.ts`, run on submission and amendment), and a Director HOD has the CEO stage auto-approved when HR approves, which makes HR's approval final (on the original order it auto-approved together with the HOD stage, and the request went straight from HOD/Retail Director to HR). Retail Director, Director, and HR stages are array-based (`retail_director_array`/`director_array`/`hr_array`, reused from Travel/Casual — any member can act, first click wins); the Director role is labeled "CEO" in emails and the dashboard nav. Approval is whole-requisition (no per-position adjustment). Introduces the app's first file-attachment handling (`lib/attachmentStorage.ts`, disk-backed under the `UPLOAD_DIRECTORY` env var): each position requires exactly one file for each of three fixed types — Job Description, KPIs, Org Chart (`EMPLOYEE_ATTACHMENT_TYPES`/`EMPLOYEE_ATTACHMENT_TYPE_LABELS` in `public/assets.ts`) — capped at 2MB each, stored at `UPLOAD_DIRECTORY/{requestId}/{positionId}/{attachmentType}/{attachmentId}/{filename}` (the per-attachment directory means a new upload can never overwrite an existing file; files from before that layout sit directly under `{attachmentType}/`, and since `file_path` is stored relative both are served the same way) and enforced one-per-type by a `UNIQUE(position_id, attachment_type)` constraint on `employee_requisition_attachments`. Each position also records Replacement/New status, a Job Grade (from `job_grades`, migration 027, managed on Settings' Employee tab, tag `GetJobGrades`; the position stores the grade name and its rank at submission in `position_job_grade_rank`, shown as "Officer (Grade 2)" by `formatJobGrade`, so re-ranking grades never renumbers an existing requisition; an amendment may keep an inactive grade a position already has), and a Salary Range in KES (min/max entered separately, stored combined as `"<min> - <max>"` by `formatSalaryRange`; `parseSalaryRange` also reads the `"<min> to <max>"` form some early rows have). Position/file validation shared by the submission and amendment routes lives in `lib/employeeRequisitionRules.ts`, and the post-submission routing both use — the self-HOD auto-approvals (applied inside the caller's transaction) and the first stage's emails — is `utils/EmployeeApprovalStages/submissionStage.ts`. The original submitter (only) can **amend** the requisition until its final stage approves — the CEO, or HR on the original order (`isEmployeeAmendable` in `lib/employeeApprovalOrder.ts` — a decline at any stage is still amendable): department, HOD, any position field, and adding/removing positions, with every target fill date re-validated as today or later. `app/api/employeerequisition/submitamendment/route.ts` takes multipart like the submission; an existing position (sent with its `positionId`) keeps every attachment it isn't sent a new file for, and a newly added position needs all three. It writes new files first, then in one transaction locks the row, re-checks the rules, records the change (migration `021_employee_requisition_amendments.sql`: `employee_requisition_amendments` with the reset decisions and, since 034, the order they were made in (`nullified_hr_before_director`), `employee_requisition_amendment_positions` per added/removed/modified position, `employee_requisition_amendment_attachments` per touched file slot), moves each replaced file's row — and those of removed positions — to `employee_requisition_archived_attachments` (the file stays on disk, viewable from the amendment history via `archived=1`), resets every stage (Retail Director to `pending` or `N/A` from the new department's flag), and re-applies the self-HOD auto-approvals. Any failure removes only that attempt's new files (`deleteStoredAttachments`) — never call `deleteRequisitionDirectory` for an existing requisition. `employee_requisitions.amendment_count` is the optimistic-concurrency token, checked under `FOR UPDATE` by the amendment route and `UpdateEmployeeStatus`. History (`lib/employeeAmendment.ts`, `EmployeeAmendmentHistory.tsx`) appears in the details modal, the `employeeview` page, the approval page and the amend form; emails show a version banner with each amendment's reason

Status transitions live in `serverActions/Update{IT,Travel,AccessRequisitionStatus}` and each fires an email via the matching `services/*EmailSender.ts`, rendered from templates in `utils/templates/`.

### Departments

`base_departments` is the department list for every form (and Travel's cost centre). Department-driven behaviour is keyed on its flag columns (migration `024_department_flags.sql`), never on department names compared in code, so a rename can't silently change routing: `requires_retail_director` (Employee Requisition's Retail Director stage), `casual_category_required` (Casual asks for a category), `requires_engineering_jobs` (Travel asks for, and stores, Engineering Jobs; displays show the jobs card whenever `engineering_jobs` is stored, never by department) and `is_active`. ### Casual requisition config

Casual locations, department location limits (`casual_department_locations`; a department with none may use every active location), sections with their budget unit (`casual_department_sections`; a department with none gets one `<department>-<location>` section), categories and daily rates live in the `casual_*` tables (migration `025_casual_config.sql`), not in code. `lib/loadCasualConfig.ts` (server-only, cached under the `GetCasualConfig` tag, throws rather than returning an empty config) loads all of it; `lib/casualConfig.ts` holds the client-safe rules both the form and the server apply to it (`getCasualSections`, `getBudgetUnitForSection`, `resolveCasualRate`, ...), so the estimate a submitter sees and the stored figure can't drift. Rates are rules in `casual_rates` with nullable department/location/category ("any"): the most specific match wins (department > location > category), then the latest `effective_from` on or before the submission or amendment date in Africa/Nairobi (`nairobiToday`). A rate change is a new row; existing rows are never edited, and each section stores the rate it was priced at. The form sends the rate it showed as `expectedRatePerDay`; `validateCasualFormData` (`lib/casualRequisitionRules.ts`) rejects a mismatch with a 409 so the submitter reviews the new totals, and the form refetches the config on any failed submit. Rows are deactivated (`is_active`), never renamed or deleted, since requisitions store names and amendments match sections by name; an amendment may keep an inactive location, category or section it already has (`CasualCurrentValues`). The public casual guideline page lists the current rates through `CasualRateCard` (`loadPublicCasualRates`, which returns the rates alone), since that page is statically built.

Each tab's "Recent changes" comes from `loadConfigChanges(tables)`, and a failed load renders `LoadError`. The Audit log tab (`serverActions/AuditLogAdmin.ts`) pages through all of `config_changes` (filterable by table, with before/after JSON) and `report_downloads`. The tabs share their UI pieces in `components/Settings/SettingsPrimitives.tsx`, and their dropdowns are `components/Select.tsx` (an accessible listbox with keyboard, type-ahead and search from 8 options), not native `<select>`. `Select` is the app's one dropdown: the requisition forms' `FormSelect` (in `CasualRequisitionForm.tsx`) wraps it in its `rose` tone, and the `DatePicker`'s month/year header uses its `inline` appearance. `unlistedLabel` keeps showing a value no option has (e.g. an inactive department an amendment keeps). `DatePicker` takes `tone="slate"` on Settings to match its inputs. ### HOD self-selection guard in submission forms

IT, Travel, Access/Key, Casual, and Employee requisition forms auto-select a department's HOD approver (`findHodForDepartment`, which returns the HOD's email — the `hodApprover` field holds an email, shown as a name through `hodNameLabel` — defined in `components/Modules/Retail/CasualRequisitionForm.tsx` and reused by the other four) and offer the rest of `hodArray` as a manual-override dropdown. Before either happens, `excludeSubmitterFromHodArray` (same file) filters the loaded `hodArray` down to exclude any entry whose email matches the logged-in submitter's (case-insensitively) — so an HOD submitting their own requisition neither gets auto-selected as their own approver nor can pick themselves from the dropdown. `loadHodArray` is called from these client components, so it is session-gated and deliberately returns no `hod_uuid` (the approval token). This is a UI-only guard; server-side, the self-HOD auto-approve branch compares emails with `sameEmail` (`lib/hodAssignment.ts`). The existing `hodEmail === userEmail` checks elsewhere in the approval-stage code remain notification-dedup only (skip a duplicate email when the HOD and submitter are the same person at a later stage), not an approval-stage bypass.

### Email

`services/EmailService.ts` / `services/EmailSender.ts` are the shared send path; every email in the app goes through `sendEmail` in `EmailService.ts`, never a direct Graph call. Setting `NOTIFICATION_EMAILS_ENABLED=false` (any case; missing or any other value sends, and an unrecognised value logs a warning) turns off every email: `sendEmail` logs the sender, recipients and subject (never the body, which carries approval tokens and verification codes) and returns `{ success: false, skipped: true }`. Reporting failure is deliberate, so callers that act on success don't treat an unsent email as delivered: the monthly salary advance export leaves rows unexported, and an email change request isn't saved. While emails are off, salary advance verification codes aren't delivered, so the advance form can't be used. `AccessEmailSender`, `AdvanceEmailSender`, `ITEmailSender`, `CasualEmailSender`, `EmployeeEmailSender`, `EmailChangeRequestEmailSender` are per-flow wrappers. Sends go through Nodemailer and/or Microsoft Graph `Mail.Send` — the Graph calls authenticate via `@azure/msal-node`'s client-credentials flow in `services/EmailService.ts` — with sender addresses set per flow via `EMAIL_SENDER`, `IT_EMAIL_SENDER`, `ACCESS_EMAIL_SENDER`, `ADVANCE_EMAIL_SENDER`, `CASUAL_EMAIL_SENDER`, `EMPLOYEE_EMAIL_SENDER`. Employee Requisition emails never include attachments — only links to them (`api/employeerequisition/attachment/[attachmentId]`) — due to Microsoft Graph payload size limits. Casual Requisition is the one flow that does attach a file: on final HR approval, `sendEmail`'s `attachments` param (Graph `fileAttachment`, base64-encoded) carries a server-rendered PDF (`@react-pdf/renderer`'s `renderToBuffer`) to the HR approver and to `EXTERNAL_CASUAL_PROVIDER`, an external casual-labor provider notified for action on every approved casual requisition.

The actual Graph call lives in `services/GraphMailClient.ts` (`sendGraphMail`): one shared MSAL client, at most 2 concurrent sends per PM2 worker (Exchange caps ~4 concurrent requests per mailbox), a 30s per-attempt timeout, and up to 4 attempts with backoff for 429 (honouring `Retry-After`), 5xx, network failures and token-acquisition failures; other 4xx fail immediately. A timed-out attempt may still have been delivered, so a retry can rarely duplicate an email. Callers that `await` a send can now wait noticeably longer during an outage (worst case ~2 minutes) before getting `{ success: false }`. Don't add another direct `fetch` to `sendMail`.

`sendEmail` wraps every email with `withNoReplyNotice` (`utils/templates/NoReplyNotice.ts`): a slim "automated, don't reply" line at the top (after a hidden subject preheader so inbox previews stay useful) and an "unmonitored mailbox - open Hotpoint Apps Hub" footer linking `NEXT_PUBLIC_BASE_URL`. Emails that set `replyTo` are skipped, since replies to those go somewhere real. Templates must not add their own do-not-reply text.

### Reports

`/dashboard/reports` (`components/Reports/ReportsPage.tsx`) lets authorized personnel (auditors) download one Excel report at a time — Travel, IT, Key & Access, Casual, Employee, or Salary Advances — for a range of submission dates, with an optional status filter (approved/declined/pending, bucketed per report from its stage statuses). `lib/reports/definitions.ts` is the client-safe registry: each report has its **own** role (`reports-travel`, `reports-it`, `reports-access`, `reports-casual`, `reports-employee`, `reports-advance`, seeded by migration `022_requisition_reports.sql` and assigned by hand). Owner roles such as `it` or `hr-advance` deliberately don't unlock a report. The page redirects anyone with no report role, the sidebar, mobile drawer and `DashboardBrand` launcher show the link only to report-role holders (`canViewReports`), and `GET /api/reports/[type]?from&to&status` re-checks the report's role on every request. Each successful download is logged to `report_downloads` in the same request (no log row, no file).

Dates are inclusive **Africa/Nairobi** calendar days, at most 12 months per report (`getReportRangeError`, shared by page and route). The SQL lives in `lib/reports/queries/*.ts` (server-only, one row per requisition — per section for Casual, per position for Employee), built from the helpers in `lib/reports/sql.ts`: `createdInRange` converts the Nairobi bounds to stored timestamps so the `request_created_at` indexes still apply, and timestamps/dates are returned as **Excel serial numbers** (`excelDateTime`/`excelDate`) so no JavaScript `Date` or server time zone is involved. `lib/reports/workbook.ts` writes real numbers and dates with display formats (not `TO_CHAR` text), freezes and filters the header row, and appends a "Report Info" sheet (range, filter, generated by/at). Amendment and push-back histories are text columns, one line per event; Travel's changed-field labels come from `TRAVEL_AMENDMENT_FIELDS`. `schemas/reports/Casual_Requisitions_Report.sql` is the ad-hoc SQL the Casual report was adapted from. The IT dashboard's all-time `requisitions-export` is separate and unchanged.

### Analytics

`/dashboard/analytics/[type]` (`components/Analytics/AnalyticsPage.tsx`; `/dashboard/analytics` redirects to the first allowed type) shows company-wide charts per requisition type, built with Recharts. `lib/analytics/definitions.ts` is the client-safe registry, shaped like the Reports one: each dashboard has its **own** role (`analytics-travel`, `analytics-casual`, `analytics-employee`, `analytics-it`, migration `035_analytics_roles.sql`, assigned on Settings' Users & roles tab), and no other role unlocks one (not config-admin, a report role or an approver array). A new dashboard needs an entry in `ANALYTICS`, `ANALYTICS_LOADERS` and `AnalyticsData`, plus a role. The page redirects anyone without the role, the nav shows the link only to role holders (`canViewAnalytics`), and `GET /api/analytics/[type]?from&to&department` re-checks the role on every request. Filters live in the URL: inclusive Africa/Nairobi submission dates, at most 12 months (the Reports rule, `getReportRangeError`), and an optional department (`loadAllDepartmentNames`, inactive ones included); unusable URL filters fall back to the last 12 months. All aggregation happens in SQL (`lib/analytics/queries/*.ts`, server-only, reusing `createdInRange`/`nairobi` from `lib/reports/sql.ts`); the route returns totals and breakdowns, never rows. "Approved" means the final stage approved — for Employee, in each requisition's own order (`hr_before_director`); for Travel, as the Travel report buckets it, with `N/A` counting as done (Director outside Tier 3, and HR on Tier 1 trips from before HR became mandatory) — "declined" that any stage declined. Travel spend is the stored `travel_total_cost` and its parts, and turnaround counts from the latest amendment, which restarts the chain. IT counts a request accepted when IT accepts it (`accepted`, or the older `approved`) and declined on a HOD decline or IT rejection, as the IT report does; completion is set in bulk by the `itrequisition-completion` trigger, so the dashboard shows completed against awaiting completion but no completion turnaround, and measures readiness as IT accepting on or before `date_joining`. Casual amounts are the sections' stored totals, before statutory costs. The Casual page also has a Budget section that ignores the submission dates: one financial year (April to March, its own picker, default the current one) of `casual_department_budgets` against spend counted the way `GetCasualBudgetEstimate` counts it (section amount plus casuals × the department's statutory cost, in the month the engagement starts, baseline spend added), from `GET /api/analytics/casual/budget?fy&department` (same role). It sums each department's budget units, so it doesn't depend on how sections map to units. Shared SQL fragments are in `lib/analytics/sql.ts`, and the month and department charts are shared Recharts components (`components/Analytics/Charts.tsx`). Employee salary figures parse the stored range text in SQL (the twin of `parseSalaryRange`). `date_position_filled` is a target date, so there are no hire/fill KPIs. Chart cards (`components/Analytics/AnalyticsPrimitives.tsx`) always offer a table view, and the `SERIES` colors are fixed per entity (approved, requested, pending, declined).

The Employee approval page also shows a collapsible "<department> at a glance" panel (`components/Approvers/EmployeeApprovers/DepartmentOverview.tsx`) to every stage, with no role needed: the department's last 12 months from `loadEmployeeDepartmentOverview`, the same queries with the requisition under review left out (`excludeRequestId`). Approval links work without a session, so it returns only what the panel shows (counts, approved salary totals, grades, new/replacement, the last 5 approved positions), and the page starts it only after the token, stage and still-pending checks. It's passed to the client as a promise and read with `use()` inside `Suspense`, so it never delays the page, and a failure shows a note instead of breaking the review.

### Salary advance submission window

New requests may only be submitted from the 1st to the 10th of each month, inclusive, in Africa/Nairobi time (`lib/salaryAdvanceWindow.ts`, all date math in SQL). A manual extension keeps the window open through `salary_advance_settings.extended_until` (single-row table, migration `023_salary_advance_submission_window.sql`, set on Settings' Salary advance tab — `serverActions/AdvanceConfigAdmin.ts`, config admins only, from today to the end of next month, or ended early); it's a date rather than a flag so a forgotten extension ends by itself. **Staff must never learn the extension exists** (it would encourage late submissions): no staff-facing text, error message or action result mentions it, and `GetAdvanceSubmissionWindow` returns only `isOpen`, the repayment date bounds and the reopen date. Outside the window `SalaryAdvanceClient.tsx` swaps the "Submit New Request" form for a closed notice; verification, request history, alterations (switch/reduce/delete) and email change requests stay available. `SubmitAdvanceForm` is the real gate and re-checks the window, plus the repayment start date: from the 15th of the current month (or today, if later — only possible during an extension) to the last day of next month. The scheduled export runs on or after the 11th; anything submitted during a later extension goes out in the next month's export via the `exported` flag. (The old `salary_advance_metadata.lock_advance_form` gate was dropped in migration `006_salary_advance_export_flag.sql` and is unrelated to this.)

### Salary advance active-request lock, self-service alterations, and the export flag

The HR side of salary advances — `GetSalaryAdvanceData`, `GetSalaryAdvanceCounts`, `ReviewSalaryAdvance`, `BatchReviewSalaryAdvance` and `api/salaryadvance/export-data` — requires the `hr-advance` role on the server (`getHrAdvanceSession`/`HR_ADVANCE_ROLE` in `lib/salaryAdvanceAccess.ts`), not just the dashboard's UI gate, since server actions are directly callable.

`serverActions/PublicServerActions/SubmitAdvanceForm.ts` blocks a new submission while the staff member (identified by `staff_number`) has an active request — `approval_status != 'declined'` — whose installment period hasn't elapsed: a `continuous` request blocks indefinitely (no end date), a `oneoff` request blocks until `repayment_start_date + no_of_installments` months has passed. This check, plus the alteration-eligibility lookup below, share their "months elapsed/remaining" logic via `lib/salaryAdvanceRules.ts` rather than duplicating the SQL.

Both `salary_advances` and `salary_advance_alterations` carry an `exported` boolean (migration `006_salary_advance_export_flag.sql`), which `app/api/triggers/send-advance-requests/route.ts` uses instead of a calendar-month filter now that submissions have no monthly cutoff: it pulls every row with `exported = false` and `hr_reviewed_at IS NULL` (plus, unconditionally, every non-declined `continuous` request — those must keep reappearing every run as a standing deduction reminder) and flips the flag to `true` only after the email actually sends successfully, so a failed send doesn't silently drop rows from future exports. `salary_advances.hr_reviewed_at` (migration `013_salary_advance_hr_reviewed.sql`) is set whenever HR approves or declines a request (`ReviewSalaryAdvance.ts`/`BatchReviewSalaryAdvance.ts`) purely to exclude already-reviewed rows from that sweep — it's a separate signal from `exported`, which keeps meaning "actually appeared in a sent export" for the dashboard's Exported badges/filters and never gets written by the review actions themselves. The manual `app/api/salaryadvance/export-data/route.ts` report deliberately does **not** apply the `hr_reviewed_at` exclusion even in its `scope=unexported` mode — that route is a reporting/analysis tool, so its only gates are whatever the caller explicitly picks (date range, or the unexported-scope toggle, which is a plain `exported = false` filter); the `hr_reviewed_at` suppression is specific to stopping the automated monthly send from re-notifying HR/Finance about rows already acted on.

Instead of waiting out that lock, a staff member can request a self-service **alteration** to an eligible active request from the "Modify Existing Request" toggle in `components/SalaryAdvance/SalaryAdvanceClient.tsx` (`SalaryAdvanceAlterationSection.tsx`): switch an active `continuous` request to `oneoff`, reduce the remaining installments of an active `oneoff` request that has more than one installment left, or — new — delete a request outright while it's still `approval_status = 'pending'` and `exported = false` (a single request can offer more than one of these at once, e.g. a pending, unexported continuous request can both switch and delete). `serverActions/PublicServerActions/GetAlterationEligibility.ts` computes which of the staff's requests qualify for which actions (empty result drives a fallback UI); `serverActions/PublicServerActions/SubmitAlterationRequest.ts` re-validates eligibility server-side before applying the change. Switch/reduce alterations only insert an audit row into `salary_advance_alterations` (FK to `salary_advances.request_id`) when the underlying request was already `exported = true` at alteration time — an alteration on a not-yet-exported request just mutates the `salary_advances` row in place, since there's no prior export to reconcile. Deletion is a hard `DELETE` with no audit row (nothing to reconcile — the row never went out). Alterations take effect immediately — no HR approval step, no email.

### Salary advance phone number

`salary_advances.staff_phone_number` is nullable (migration `019_salary_advance_optional_phone.sql`). It's only collected, and then required, when the request is repaid over more than one installment (`isAdvancePhoneRequired` in `public/assets.ts`), so HR/Finance can follow up on multi-month repayments; it may also be used to disburse the advance via M-Pesa. Continuous requests are always one installment, so they never have one. `SubmitAdvanceForm.ts` works out the rule from the final installments and stores `NULL` whenever the phone isn't required, even if the client sent one. The form's phone fields and the "Contact Number" policy clause appear only under that same rule. In staff-facing views (confirmation step, email, history modal) the phone row is hidden when empty. The HR modal instead uses `formatPhoneForDisplay`, which shows "Not required" (single installment) or "Not provided" (a legacy multi-installment row from before the field existed; the migration turned their `'not provided'` placeholder into `NULL`). There's deliberately no DB `CHECK` enforcing the rule: legacy rows would make every HR update on them fail.

### Salary advance email change requests

`components/SalaryAdvance/EmailChangeRequestModal.tsx` (a `ClientPortal` modal, opened from both the verification step and the signed-in form in `SalaryAdvanceClient.tsx`) submits to `serverActions/PublicServerActions/SubmitEmailChangeRequest.ts`. It is **public and unverified** — the requester proves nothing beyond knowing a staff number — so submitting it deliberately performs no write to `company_staff_data`; HR resolves it after confirming identity out of band (see the last bullet). Design points to preserve:

- Every submission is saved to `email_change_requests` (migration `015_email_change_requests.sql`), which is also the rate-limit source (per-IP and per-staff-number counts in a rolling window) and the duplicate check (an `open` request for the same staff number in the last 24h blocks a new one). Limits live in `lib/emailChangeRequest.ts`. `status` is `open`, `approved` or `rejected` (migration `030_email_change_resolution.sql`, final once resolved). If the HR email fails to send, the row is deleted so the duplicate check does not block a retry.
- An unknown staff number is accepted and flagged to HR (`staff_found = false`) rather than rejected, so the form cannot be used to enumerate valid staff numbers. A hidden honeypot field (`website`) is silently dropped.
- `services/EmailChangeRequestEmailSender.ts` sends **three separate emails** from `ADVANCE_EMAIL_SENDER`: (1) a copy of what was typed to the requested address only, with Reply-To set to it; (2) to `FIRST_HR_EMAIL`, `SECOND_HR_EMAIL` and `ADMIN_EMAIL`, the submission plus the `company_staff_data` on-file comparison and an "unverified — confirm identity by phone" warning, with **no Reply-To**; (3) a courtesy notice to the current on-file email. On-file data must never appear in an email the requested (unverified) address receives, and email (2) must not gain a Reply-To of the requested address, since a reflexive HR reply would quote the on-file details back to a possible impersonator.
- HR (role `hr-advance`) resolves requests on the salary advance HR dashboard's Email changes view (`components/SalaryAdvance/EmailChangeRequestsPanel.tsx`, `serverActions/EmailChangeRequestAdmin.ts`, run through `runHrAdvanceChange` in `lib/salaryAdvanceAccess.ts`). **Approve & apply** requires ticking that identity was confirmed and, in one transaction, sets `company_staff_data.staff_email` (refused if the staff number is missing or duplicated, or another record already uses the address, since verification codes look staff up by email), marks the old address's unused `verification_codes` consumed, and records `previous_email`/`resolved_*`; after commit `EmailChangeResolutionEmailSender` emails the new address and a notice to the replaced one. **Reject** needs a reason, which stays internal; the requester gets a generic notice. `company_staff_data` is re-imported from the HR system, so every applied change must also be made there — the UI says so. The same dashboard's Staff directory view (`StaffDirectoryPanel.tsx`, `serverActions/StaffDirectoryAdmin.ts`) searches, adds and edits staff records (never deletes; staff number and email kept unique; changes logged to `config_changes`) for fixes that can't wait for the next import. A record's department must be an active `base_departments` one (`resolveDepartment`; an edit may keep the one it has). Records are **deactivated**, never deleted (`company_staff_data.deactivated_at`/`_by`/`deactivation_reason`, migration `032_staff_deactivation.sql`; `deactivateStaffRecord` needs a reason and consumes the email's unused codes, `reactivateStaffRecord` clears them). The HR import upserts by `staff_number` and must never write those columns. A deactivated record gets the generic "if this email is on file" response and no code from `RequestVerificationCode` - its email on file is sent an "inactive, contact HR" notice instead, at most once an hour (in-memory, per worker) - fails `VerifyAdvanceCode`, and `getAdvanceFormSession` (`lib/advanceVerificationSession.ts`) returns null for it on the next request (fails open on a DB error), so an hour-long advance session already issued stops too.
- All requester-supplied values are HTML-escaped in `utils/templates/EmailChangeRequestTemplate.ts`. `sendEmail` gained an optional `replyTo` for this flow.

### Embedded SSO portals

The HelpDesk and Staff Product Purchase dashboard pages render an iframe against an internally reverse-proxied SSO URL (`SSO_SHARED_SECRET`) — they're portals into separate internal systems, not requisition forms, and don't follow the requisition/approval patterns above.

- The iframe `src` is `/api/embed/<app>` (`app/api/embed/[app]/route.ts`), which signs the hand-off when the iframe requests it and redirects (`no-store`) to the app's SSO endpoint. Never render a signed URL into the page itself: back/forward navigation reuses the rendered page and would replay a timestamp past the embedded apps' 2-minute window.
- Each embedded app verifies its own signing format, configured per app in that route: Staff Product Purchase signs `email:timestamp`; HelpDesk signs `JSON.stringify([email, name, timestamp])` (it uses `name` to seed new-user registration). Changing either format means deploying the host and that app together.
- Staff Product Purchase also calls back into this app, server-to-server, through `POST /api/staff/lookup` (`app/api/staff/lookup/route.ts`): `{ email }` or `{ staffNumber }` (case/space-insensitive) → `{ found: false }` or `{ found, active, staff: { staffNumber, name, department } }`, gated by the `x-staff-lookup-key` header matching `STAFF_LOOKUP_API_KEY` (refuses everything while unset; 503 on a DB error). It never returns the record's email, since a caller looking up by staff number mustn't learn the personal email on file. Staff Product Purchase uses it to gate registration and refuse sign-in for deactivated records, so changing its response shape means deploying both.
