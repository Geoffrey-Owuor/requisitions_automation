## Architecture

Hotpoint Apps Hub is an internal Next.js 16 (App Router) portal for submitting/approving requisitions — IT equipment, travel, salary advances, and physical access/keys — plus two SSO-embedded internal systems (IT HelpDesk, Staff Product Purchase).

### Auth & session model

- Sign-in is a manual Microsoft Entra ID OAuth/PKCE flow using `arctic` (`app/api/auth/login`, `app/api/auth/callback`).
- After the Entra callback, the app issues its **own** session: a `jose`-signed JWT in an httpOnly cookie `requisitions_session` (`lib/session.ts`, 7-day expiry). All server-side auth checks read this cookie, not the Entra token.
- Route gating is `proxy.ts` at the repo root, **not** `middleware.ts` — Next.js 16 renamed the convention. It redirects unauthenticated `/dashboard/*` to `/login`, and bounces already-authenticated users away from `/`, `/login`, `/advance`.
- `app/(protected)/dashboard/layout.tsx` is the second gate: re-checks the session, loads roles via `serverActions/GetUserRoles.ts` (Postgres join `users` → `user_roles` → `roles`, defaults to `["user"]`), and wraps children in `UserProvider` (`context/UserContext.tsx`).
- The same layout also computes `ApproverMemberships` via `serverActions/GetApproverMemberships.ts` (`lib/approverMemberships.ts`) — per-array approver flags (HOD — any `hod_array` row, assigned-HOD candidate or alternate; Security, IT, Director, Retail Director, plus per-form HR permissions) found by checking the session email against each stage's `_array` table — and passes it into `UserProvider` alongside roles.
- `(approvers)` route group (`accessapproval/[uuid]`, `itapproval/[uuid]`, `travelapproval/[uuid]`) is reached via emailed links and is token-gated per-UUID, independent of the logged-in session — don't assume `getSession()` applies there.

### Route groups (`app/`)

- `(protected)/dashboard` — authenticated area. Nested groups: `(embeddings)` (HelpDesk / Staff Purchase SSO iframes), `(pdfs)` (PDF viewers, e.g. `casualpdf`), plus `advance` (salary advance) and `employeeview` (session-gated, read-only Employee Requisition viewer — no PDF export, so it deliberately lives outside `(pdfs)`).
- `(approvers)` — public, per-UUID approval pages for approvers acting on emailed links (`casualapproval`, `employeeapproval`, etc.).
- `advance/page.tsx` and `login/page.tsx` are public entry points gated by `proxy.ts`.
- `api/` — form submission routes (`{access,it,travel,casual,employee}requisition/submitrequisition`), auth routes, mail triggers, `CRON_SECRET`-gated scheduled triggers (`api/triggers/*`), `REVALIDATE_TAG_KEY`-gated cache revalidation (`api/revalidate-tag`), and `api/employeerequisition/attachment/[attachmentId]` — an authenticated file-streaming route (session or approver-token gated) since Employee Requisition attachments are stored on disk under `UPLOAD_DIRECTORY`, outside `public/`. Its `/preview` sub-route renders `.doc`/`.docx` and `.xls`/`.xlsx` attachments as inline HTML (via `mammoth` and `exceljs` respectively) instead of forcing a download; other file types fall back to a "use Download" page.

### Dashboard tables & navigation

`components/Dashboard/UserDashboard.tsx` renders one table per requisition type and approval stage the signed-in user can see (their own submissions, plus any pending-approval queues their `roles`/`ApproverMemberships` qualify them for). Each requisition type has its own `{Type}RequisitionsDashboard/` folder under `components/Dashboard/` (table + details modal) — `TravelRequisitionsTable.tsx`/`TravelDetailsModal.tsx` sit directly under `components/Dashboard/`, while IT, Access, Casual, and Employee each have their own subfolder. `lib/dashboardTables.tsx`'s `DASHBOARD_TABLES` registry lists every possible table (key, label, icon) in DOM order; `components/Dashboard/DashboardTableNav.tsx` renders a sticky jump-nav built from whichever of those are actually visible for the current user, shown only once 3 or more tables are visible. `useTableCollapseStore` persists each table's collapsed/expanded state.

Each requisition type also has one read-only **approval history** table (`dataFlag: "history"`, keys `{type}-history`) for approvers, scoped server-side in `serverActions/Get{Type}RequisitionData.ts` to the union of every stage the user is involved in: rows where they are the assigned HOD (whoever acted) or acted on the HOD stage as an alternate, plus — per stage membership/role — every request that reached (or was auto-approved past) that stage. Conditional stages only see their own requests (Travel Director: Tier 3 only; Retail Director: retail only), and requests declined before a stage are hidden from it. IT history is HOD-only because IT admins already get the full history (with export) from `itAll`. History modals map `history` to the `"user"` stage, so they never offer an approval action. Every non-`userData` flag is checked on the server (role or `_array` membership), never trusted from the dashboard's UI gate. That includes IT's `itPending`/`itAll` and `requisitions-export` (role `it`) and Travel's `hrPending`/`directorPending` (roles `hr-travel`/`director`).

### Approval workflows

The HOD stage is not array-based: it belongs to the single **assigned** HOD auto-selected (or manually overridden) at submission and stored on the requisition row (`*_hod_email` / `hod_approver_email`), plus that HOD's permanent **alternates** (migration `018_hod_alternates.sql`). Alternates are themselves `hod_array` rows (so their `hod_uuid` is their approval token) linked through `hod_alternates(hod_id, alternate_id)`; rows flagged `hod_array.is_alternate_only` are never offered in the submission dropdown/auto-select (`loadHodArray`) and are rejected by the server-side HOD lookups (`resolveHod` and the submission routes). The assigned HOD and all alternates (minus the submitter) get the "Action Required" email and see the request in their pending queue; first click wins. The update actions (`serverActions/Update*Status.ts`) enforce this with `getHodActionError` (`lib/hodAssignment.ts`): the actor must be the assigned HOD or one of their alternates — not merely in `hod_array` — and never the submitter. Acting on the HOD stage no longer overwrites the assigned HOD email; the actor's email goes in `*_hod_actioned_by_email` (the `*_hod_approver`/`hod_approver_name` name column is still overwritten with the actor's name, so displays show who acted). Only the actor gets the HOD-stage confirmation, and every later-stage email (and Travel push-back email) goes to the actor, not the assigned HOD. HOD history shows the assigned HOD everything assigned to them and an alternate only what they acted on (`hodPendingScopeSql`/`hodHistoryScopeSql`); detail/attachment access goes through `isHodViewer`. Because the name column holds the actor, Travel/Casual amendments resolve the assigned HOD's name from its email (`assignedHodNameSql`) for prefill and diffing, and an amendment resets `*_hod_actioned_by_email`. Alternates are managed directly in the DB (refresh via the `GetHodArray` tag). The dashboard's HOD tables are gated on `ApproverMemberships.isHodApprover`, not the legacy `hod` role. Every stage after the HOD stage — IT, Security, HR, Director, Retail Director — is fully array-based: `ApproverMemberships` checks membership by exact email match against that stage's `_array` table, and any member of that array can act on a pending item (first click wins, no "assigned to me" column).

Each requisition type has its own multi-stage chain under `utils/`:

- `utils/ITApprovalStages/` — hodApprovalStage → itApprovalStage
- `utils/AccessApprovalStages/` — hodApprovalStage → securityApprovalStage
- `utils/TravelApprovalStages/` — hodApprovalStage → hrApprovalStage → directorApprovalStage. HOD and HR are mandatory for every tier (`hodApprovalStage` always forwards to HR); only the cost tier from `utils/calculateTravelApprovalTier.ts` decides whether Director is added — Tier 1 (≤30K) and Tier 2 (30K–100K) finalize at HR, Tier 3 (≥100K) adds Director. Any travel-HR member can **push back** (reverse) the recorded HR decision, approved ↔ declined (it must flip the status), from a Push-back button in the dashboard's travel history modal. The button opens the HR approval page with `&mode=pushback`; that parameter is presentation only. `serverActions/PushbackTravelHrDecision.ts` makes the change in one transaction with no intermediate `pending` state: it resolves the actor from the HR token, locks the row, re-checks the rules in `lib/travelPushback.ts`, copies the old decision into `travel_hr_pushbacks` (migration `016_travel_hr_pushbacks.sql`) and overwrites the `travel_hr_*` columns. The rules: HR status not pending, not Tier 3 (even if the Director stage was auto-approved), fewer than 3 push-backs, and on or before `travel_departure_date` in Africa/Nairobi time. `travel_hr_pushback_count` doubles as the optimistic-concurrency token. Emails go out via `utils/TravelApprovalStages/hrPushbackStage.ts`: to the actor, submitter and HOD, plus Finance — a dedicated "Reversed" email for approved → declined, or the normal final-approval email for declined → approved. Push-back history (`components/Approvers/TravelApprovers/TravelPushbackHistory.tsx`) is shown in the details modal, the approval page, the PDF view and generated PDF, and the travel email template. The original submitter (only) can also **amend** any form field until HR approves (a HOD or HR decline is still amendable) and on or before the departure date — rules in `lib/travelAmendment.ts`, which reuses the push-back departure-date window. `app/api/travelrequisition/submitamendment/route.ts` locks the row, re-checks the rules, recomputes the tier server-side, resets every approval stage (HOD/HR `pending`; Director `pending` for Tier 3, else `N/A`), reproduces the self-HOD auto-approve branch, and records the change in `travel_requisition_amendments` (reason, tier/total before and after, snapshot of the decisions it reset) plus one `travel_requisition_amendment_fields` row per changed field keyed by the `TravelFormData` key (migration `017_travel_requisition_amendments.sql`). Push-back history and `travel_hr_pushback_count` survive an amendment — the 3-push-back cap is for the requisition's life. `travel_requisitions.amendment_count` is a second optimistic-concurrency token, checked under `FOR UPDATE` by the amendment route, `UpdateTravelStatus` and `PushbackTravelHrDecision`, so no approver or push-back acts on content amended mid-review. Emails go out via `utils/TravelApprovalStages/amendmentStage.ts`. Amendment history (`TravelAmendmentHistory.tsx`) appears everywhere push-back history does; the dashboard modal loads both through `serverActions/GetTravelAuditTrail.ts`. Validation shared by the submission and amendment routes lives in `lib/travelRequisitionRules.ts`
- `utils/CasualApprovalStages/` — hodApprovalStage → hrApprovalStage (no Finance stage, no tiering); like every other flow, the HOD stage is the single HOD selected at submission (stored in `casual_hod_email`), and only HR is array-based (`hr_array` — any member can act, first click wins). On HR approval, a generated PDF summary is attached to the HR approver's confirmation email and to a notification sent to the external casual-labor provider (`EXTERNAL_CASUAL_PROVIDER`); `loadFinanceArray()` in `lib/loadAppDataV2.ts` is kept but unused by this flow. The original submitter (only) can amend the requisition — any header field or section — any time until HR approves it (`isCasualAmendableHrStatus` in `public/assets.ts` — a HOD or HR decline is still amendable; a HOD approval is not a barrier). Amending fully resets both `casual_hod_*` and `casual_hr_*` approval columns to `pending`/`NULL` and restarts the chain from HOD (reproducing the self-HOD auto-approve branch when the re-resolved HOD is the submitter), recording a diff row per amendment in `casual_requisition_amendments` (header fields) and `casual_requisition_amendment_sections` (per-section fields, matched by the now-stable `UNIQUE(request_id, section_name)` identity) via `utils/CasualApprovalStages/amendmentStage.ts` and `app/api/casualrequisition/submitamendment/route.ts`. `casual_requisitions.amendment_count` doubles as an optimistic-concurrency token — both the amendment route and `UpdateCasualStatus` check it under `FOR UPDATE` so an approver can't act on a version superseded mid-review. There is no mechanism to change a requisition once HR has approved it (this is an accepted gap, not an oversight) and no submitter-initiated withdrawal — a corrective amendment is the only way to undo one. This replaced the earlier "HR can adjust the final approved headcount per section" behavior (and the `hr_approved_casuals` column), since changes now have to originate from the submitter
- `utils/EmployeeApprovalStages/` — hodApprovalStage → retailDirectorApprovalStage → directorApprovalStage → hrApprovalStage. Retail Director is conditional: it only applies to requests from a retail department, and is skipped even then if the HOD is themself a Retail Director. Director and HR are mandatory for every request; if the HOD is also a Director, both the Retail Director and Director stages auto-approve and the request jumps straight to HR. Retail Director, Director, and HR stages are array-based (`retail_director_array`/`director_array`/`hr_array`, reused from Travel/Casual — any member can act, first click wins); the Director role is labeled "CEO" in emails and the dashboard nav. Approval is whole-requisition (no per-position adjustment). Introduces the app's first file-attachment handling (`lib/attachmentStorage.ts`, disk-backed under the `UPLOAD_DIRECTORY` env var): each position requires exactly one file for each of three fixed types — Job Description, KPIs, Org Chart (`EMPLOYEE_ATTACHMENT_TYPES`/`EMPLOYEE_ATTACHMENT_TYPE_LABELS` in `public/assets.ts`) — capped at 2MB each, stored at `UPLOAD_DIRECTORY/{requestId}/{positionId}/{attachmentType}/{filename}` and enforced one-per-type by a `UNIQUE(position_id, attachment_type)` constraint on `employee_requisition_attachments`. Each position also records Replacement/New status, a Job Grade (fixed 9-grade list, `JOB_GRADES` in `public/assets.ts`), and a Salary Range in KES (min/max entered separately, stored combined as `"<min> to <max>"`)

Status transitions live in `serverActions/Update{IT,Travel,AccessRequisitionStatus}` and each fires an email via the matching `services/*EmailSender.ts`, rendered from templates in `utils/templates/`.

### Two approver-loading paths — check which one applies

`lib/loadAppData.ts` (JSON-backed, reads `data/*.json`) and `lib/loadAppDataV2.ts` (Postgres-backed, wrapped in `unstable_cache`) export functions with the **same names** (`loadHodArray`, `loadHrArray`, `loadITArray`, `loadDirectorArray`, `loadBaseDepartments`, plus V2-only `loadSecurityArray`). The DB-backed V2 is the current path; the JSON version is being phased out and `data/*.json` is gitignored — untracked in git, though local copies may still exist on a given machine from before the Postgres migration. When editing approver-loading code, check the actual import to know which module a given caller uses — don't assume based on the function name alone.

### HOD self-selection guard in submission forms

IT, Travel, Access/Key, Casual, and Employee requisition forms auto-select a department's HOD approver (`findHodForDepartment`, defined in `components/Modules/Retail/CasualRequisitionForm.tsx` and reused by the other four) and offer the rest of `hodArray` as a manual-override dropdown. Before either happens, `excludeSubmitterFromHodArray` (same file) filters the loaded `hodArray` down to exclude any entry whose email matches the logged-in submitter's — so an HOD submitting their own requisition neither gets auto-selected as their own approver nor can pick themselves from the dropdown. This is a UI-only guard: the existing `hodEmail === userEmail` checks elsewhere in the approval-stage code remain notification-dedup only (skip a duplicate email when the HOD and submitter are the same person at a later stage), not an approval-stage bypass.

### Email

`services/EmailService.ts` / `services/EmailSender.ts` are the shared send path; every email in the app goes through `sendEmail` in `EmailService.ts`, never a direct Graph call. Setting `NOTIFICATION_EMAILS_ENABLED=false` (any case; missing or any other value sends, and an unrecognised value logs a warning) turns off every email: `sendEmail` logs the sender, recipients and subject (never the body, which carries approval tokens and verification codes) and returns `{ success: false, skipped: true }`. Reporting failure is deliberate, so callers that act on success don't treat an unsent email as delivered: the monthly salary advance export leaves rows unexported, and an email change request isn't saved. While emails are off, salary advance verification codes aren't delivered, so the advance form can't be used. `AccessEmailSender`, `AdvanceEmailSender`, `ITEmailSender`, `CasualEmailSender`, `EmployeeEmailSender`, `EmailChangeRequestEmailSender` are per-flow wrappers. Sends go through Nodemailer and/or Microsoft Graph `Mail.Send` — the Graph calls authenticate via `@azure/msal-node`'s client-credentials flow in `services/EmailService.ts` — with sender addresses set per flow via `EMAIL_SENDER`, `IT_EMAIL_SENDER`, `ACCESS_EMAIL_SENDER`, `ADVANCE_EMAIL_SENDER`, `CASUAL_EMAIL_SENDER`, `EMPLOYEE_EMAIL_SENDER`. Employee Requisition emails never include attachments — only links to them (`api/employeerequisition/attachment/[attachmentId]`) — due to Microsoft Graph payload size limits. Casual Requisition is the one flow that does attach a file: on final HR approval, `sendEmail`'s `attachments` param (Graph `fileAttachment`, base64-encoded) carries a server-rendered PDF (`@react-pdf/renderer`'s `renderToBuffer`) to the HR approver and to `EXTERNAL_CASUAL_PROVIDER`, an external casual-labor provider notified for action on every approved casual requisition.

### State management split

- Server data: TanStack React Query (`components/QueryProvider.tsx`), fed by `serverActions/`.
- Client-only UI state: Zustand stores in `store/` (`useAlertStore`, `useLoadingStore`, `useToggleStore`) — these do not hold server data.
- `utils/ApiHandler.ts` is a thin fetch wrapper for client components calling internal `api/` routes, as distinct from calling server actions directly.

### Salary advance submission window

Submissions are not time-gated: there is no submission deadline, and the old `salary_advance_metadata.lock_advance_form` gate (and the table itself, plus its dead `salary_advance_otp` column) was dropped in migration `006_salary_advance_export_flag.sql`. HR still batches processing once a month, but nothing in code enforces a submission cutoff.

### Salary advance active-request lock, self-service alterations, and the export flag

`serverActions/PublicServerActions/SubmitAdvanceForm.ts` blocks a new submission while the staff member (identified by `staff_number`) has an active request — `approval_status != 'declined'` — whose installment period hasn't elapsed: a `continuous` request blocks indefinitely (no end date), a `oneoff` request blocks until `repayment_start_date + no_of_installments` months has passed. This check, plus the alteration-eligibility lookup below, share their "months elapsed/remaining" logic via `lib/salaryAdvanceRules.ts` rather than duplicating the SQL.

Both `salary_advances` and `salary_advance_alterations` carry an `exported` boolean (migration `006_salary_advance_export_flag.sql`), which `app/api/triggers/send-advance-requests/route.ts` uses instead of a calendar-month filter now that submissions have no monthly cutoff: it pulls every row with `exported = false` and `hr_reviewed_at IS NULL` (plus, unconditionally, every non-declined `continuous` request — those must keep reappearing every run as a standing deduction reminder) and flips the flag to `true` only after the email actually sends successfully, so a failed send doesn't silently drop rows from future exports. `salary_advances.hr_reviewed_at` (migration `013_salary_advance_hr_reviewed.sql`) is set whenever HR approves or declines a request (`ReviewSalaryAdvance.ts`/`BatchReviewSalaryAdvance.ts`) purely to exclude already-reviewed rows from that sweep — it's a separate signal from `exported`, which keeps meaning "actually appeared in a sent export" for the dashboard's Exported badges/filters and never gets written by the review actions themselves. The manual `app/api/salaryadvance/export-data/route.ts` report deliberately does **not** apply the `hr_reviewed_at` exclusion even in its `scope=unexported` mode — that route is a reporting/analysis tool, so its only gates are whatever the caller explicitly picks (date range, or the unexported-scope toggle, which is a plain `exported = false` filter); the `hr_reviewed_at` suppression is specific to stopping the automated monthly send from re-notifying HR/Finance about rows already acted on.

Instead of waiting out that lock, a staff member can request a self-service **alteration** to an eligible active request from the "Modify Existing Request" toggle in `components/SalaryAdvance/SalaryAdvanceClient.tsx` (`SalaryAdvanceAlterationSection.tsx`): switch an active `continuous` request to `oneoff`, reduce the remaining installments of an active `oneoff` request that has more than one installment left, or — new — delete a request outright while it's still `approval_status = 'pending'` and `exported = false` (a single request can offer more than one of these at once, e.g. a pending, unexported continuous request can both switch and delete). `serverActions/PublicServerActions/GetAlterationEligibility.ts` computes which of the staff's requests qualify for which actions (empty result drives a fallback UI); `serverActions/PublicServerActions/SubmitAlterationRequest.ts` re-validates eligibility server-side before applying the change. Switch/reduce alterations only insert an audit row into `salary_advance_alterations` (FK to `salary_advances.request_id`) when the underlying request was already `exported = true` at alteration time — an alteration on a not-yet-exported request just mutates the `salary_advances` row in place, since there's no prior export to reconcile. Deletion is a hard `DELETE` with no audit row (nothing to reconcile — the row never went out). Alterations take effect immediately — no HR approval step, no email.

### Salary advance phone number

`salary_advances.staff_phone_number` is nullable (migration `019_salary_advance_optional_phone.sql`). It's only collected, and then required, when the request is repaid over more than one installment (`isAdvancePhoneRequired` in `public/assets.ts`), so HR/Finance can follow up on multi-month repayments. It isn't used for disbursement. Continuous requests are always one installment, so they never have one. `SubmitAdvanceForm.ts` works out the rule from the final installments and stores `NULL` whenever the phone isn't required, even if the client sent one. The form's phone fields and the "Contact Number" policy clause appear only under that same rule. In staff-facing views (confirmation step, email, history modal) the phone row is hidden when empty. The HR modal instead uses `formatPhoneForDisplay`, which shows "Not required" (single installment) or "Not provided" (a legacy multi-installment row from before the field existed; the migration turned their `'not provided'` placeholder into `NULL`). There's deliberately no DB `CHECK` enforcing the rule: legacy rows would make every HR update on them fail.

### Salary advance email change requests

`components/SalaryAdvance/EmailChangeRequestModal.tsx` (a `ClientPortal` modal, opened from both the verification step and the signed-in form in `SalaryAdvanceClient.tsx`) submits to `serverActions/PublicServerActions/SubmitEmailChangeRequest.ts`. It is **public and unverified** — the requester proves nothing beyond knowing a staff number — so it deliberately performs no write to `company_staff_data`; HR acts on the emails. Design points to preserve:

- Every submission is saved to `email_change_requests` (migration `015_email_change_requests.sql`), which is also the rate-limit source (per-IP and per-staff-number counts in a rolling window) and the duplicate check (an `open` request for the same staff number in the last 24h blocks a new one). Limits live in `lib/emailChangeRequest.ts`. `status`/`resolved_*` are reserved for a future HR view; nothing writes them. If the HR email fails to send, the row is deleted so the duplicate check does not block a retry.
- An unknown staff number is accepted and flagged to HR (`staff_found = false`) rather than rejected, so the form cannot be used to enumerate valid staff numbers. A hidden honeypot field (`website`) is silently dropped.
- `services/EmailChangeRequestEmailSender.ts` sends **three separate emails** from `ADVANCE_EMAIL_SENDER`: (1) a copy of what was typed to the requested address only, with Reply-To set to it; (2) to `FIRST_HR_EMAIL`, `SECOND_HR_EMAIL` and `ADMIN_EMAIL`, the submission plus the `company_staff_data` on-file comparison and an "unverified — confirm identity by phone" warning, with **no Reply-To**; (3) a courtesy notice to the current on-file email. On-file data must never appear in an email the requested (unverified) address receives, and email (2) must not gain a Reply-To of the requested address, since a reflexive HR reply would quote the on-file details back to a possible impersonator.
- All requester-supplied values are HTML-escaped in `utils/templates/EmailChangeRequestTemplate.ts`. `sendEmail` gained an optional `replyTo` for this flow.

### Embedded SSO portals

The HelpDesk and Staff Product Purchase dashboard pages render an iframe against an internally reverse-proxied SSO URL (`SSO_SHARED_SECRET`) — they're portals into separate internal systems, not requisition forms, and don't follow the requisition/approval patterns above.

### Path alias

`@/*` maps to the repo root (`tsconfig.json`), e.g. `@/lib/session`, `@/serverActions/GetUserRoles`.
